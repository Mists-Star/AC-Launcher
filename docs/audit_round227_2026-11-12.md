### P0-1 · 删除**正在运行**的实例不拦截 → 边跑边 `rmtree`，存档当场损坏 · 已复现

- `src/pages_instances.py:2284-2292` `_delete_instance()`：确认框 → `self.mgr.remove(inst.id)`
  → `src/instances.py:1137-1149` `_strip_shared_junctions()` + `shutil.rmtree(inst.root)`
- **全链路没有任何「该实例正在运行」检查**：`grep _game_procs src/pages_instances.py` → **0 命中**。
  进程表只存在于主窗（`src/main_window.py:5150` 启动时有双开护栏，删除侧没有对应护栏）。
- **触发**：开着游戏 → 实例页 → 删除 → 确认。Windows 上被游戏占用的文件删不掉，
  `rmtree` 会跳过一部分；`ignore_errors=True` 把异常全吞掉 →
  **一半文件被删、元数据照删**，游戏继续跑但存档/配置已残缺，
  退出时再写一次就把坏状态落盘。
- **复现**（`_scratch/_probe_delete_running.py`：`confirm` 打桩成「玩家点确定」，
  `_game_procs` 放入该实例 id，直接调 `InstancesPage._delete_instance`）：
  ```
  实例 deadbeef 正在运行（_game_procs 有它）
  mgr.remove 被调用次数 = 1 ['deadbeef']
  FAIL: 运行中的实例被直接删了 —— 没有 isRunning 拦截
  ```
- **对照**：Prism `launcher/ui/pages/instance/InstancePage.cpp` 删除前
  `m_instance->isRunning()` 拦截；HMCL 同样先 `stop()`。
- **最小修法**：`_delete_instance` 开头
  ```python
  win = self.window()
  if inst.id in getattr(win, "_game_procs", {}):
      warn(self, t("instances.delete_title"), t("instances.delete_while_running"))
      return
  ```
  另加 i18n key（中英）。`rmtree` 的 `ignore_errors=True` 建议在删除实例时改成
  `onerror=` 收集失败项并告知，别静默。

### P0-2 · 删除确认框**按回车 = 确认删除**（破坏性操作默认按钮就是「是」）· 已复现

- `src/win_rounded.py:221-228`：
  ```python
  for label in reversed(buttons):        # ("No","Yes") → 先建 Yes
      btn = QPushButton(label)
      if label == buttons[-1]:           # Yes → 还被设成 accent（视觉上最醒目）
          btn.setProperty("cls", "accent")
  ```
  Qt 里对话框内第一个 `autoDefault` 按钮会自动成为回车目标 → **Yes**。
  全程没有 `setAutoDefault(False)`、没有 `setDefaultButton(No)`、没有把焦点给「否」。
- **实测**（`_scratch/_probe_ui_danger.py`，离屏弹真对话框 + `QTest.keyClick(Key_Return)`）：
  ```
  删除确认框 defaultButton = None
  删除确认框 按回车 ->      = True        ← True = 确认删除
  自定义 ask 回车 ->        = 取消下载    ← 砸在最后一个按钮上
  ```
- **后果**：实例页误触回车（或习惯性拿回车关弹窗）= 删实例。叠加 **P0-1**，
  连「正在运行」都拦不住 → **一次回车就能删掉一个正在玩的实例**。
- **`ask()` 的语义还反着**：`ask(..., ("继续下载", "取消下载"))` 回车落在「取消下载」，
  对「退出确认」这类「最后一个是危险项」的用法，回车 = 执行危险操作。
- **对照**：Prism `EnsureDialog` 把 Cancel 设为 default；HMCL `ConfirmDialog` 同样默认取消。
- **最小修法**：`_msgbox` 给每个按钮 `setAutoDefault(False)`，并由调用点显式声明
  `default_label`（`confirm()` 一律指向否/取消）；`ask()` 加 `safe_index` 参数。

### P1-1 · 模组页「批量启用」按钮实际执行**批量禁用** · 已复现

- `src/mod_list.py:400-406` 两个按钮都走 `ui_kit.make_button(on_click=…)`
- `src/ui_kit.py:232-233` `b.clicked.connect(on_click)` —— 直连，没有参数隔离
- `src/mod_list.py:600` `def _batch_enable(self, want: bool = True)`

- **实测**：
  ```
  启用按钮实际收到的参数: [('want=', False)]
  禁用按钮实际收到的参数: [('want=', False), ('want=', False)]
  ```
- **玩家感受**：勾选 10 个已禁用模组 → 点「启用」→ 刷新后还是灰的，无提示，点几次都一样。
- **单个切换是好的**（`src/mod_list.py:230-232` 用无参 lambda），只影响批量。
- **最小修法**：
  ```python
  self.en_btn.clicked.connect(lambda *_: self._batch_enable(True))
  self.dis_btn.clicked.connect(lambda *_: self._batch_enable(False))
  ```

### P1-3 · 实例备份把**整个资源共享池**复制进快照（体积爆炸 + 破坏联接）· 已复现

- `src/core/backup.py:27` `_SKIP_DIRS = ("libraries",)`；`:91` `src = inst.mc_dir`
- **前提**：AC 自建实例的 `<mc_dir>/libraries`、`<mc_dir>/assets` 都是
  **目录联接（junction）**（`core/shared_libs.py:149-190` + `instances.py:205-230`）。
  实测属性 `attrs = 0x410`（DIRECTORY + REPARSE_POINT），`os.path.islink() == False`。
- **后果 1**：`os.walk` 对 junction **会**进入（实测 5 个文件全部来自被联接的池），
  而 `_SKIP_DIRS` 只跳了 libraries → 每次备份都整份复制
  `data/shared/assets/objects/**`（1.20 约 400~700 MB、上万文件）。
- **后果 2**：`restore_backup`（`:169-197`）先摘联接再 `copytree`，把快照里的
  `assets/` 副本写回成**真实目录** → 实例不再共享；随后 `ensure_dirs()` 把该目录
  rename 成 `assets__pending` 逐文件搬回池（`shared_libs.py:162-190`），上万次 move。
- **最小修法**：`_SKIP_DIRS = ("libraries", "assets")` + `_walk_files` 跳过
  reparse point（`os.walk` 的 `islink` 判不出来，要查 `FILE_ATTRIBUTE_REPARSE_POINT`）。
- **对照**：Prism / HMCL 的实例备份只收用户内容，可再下载资源不进快照。

### P1-4 · 外来实例跟随全局「版本隔离」→ 存档 / 模组当场"消失" · 已复现

> 这是本轮**最有解释力**的一条：同一个根因同时造成「导入整合包看不到模组」
> 与「导入 .minecraft 存档不见了」两个玩家投诉。

- **规则落点**：`src/launch.py:140-168` `resolve_game_dir()` 与
  `src/instances.py:151-190` `Instance.game_dir`（同一套口径）
  ```python
  iso = inst.isolation or settings.get("version_isolation") or "default"
  if iso == "isolated":
      return os.path.join(inst.mc_dir, "versions", sub)     # ← 外来实例也被重定向
  ```
- **根因**：`isolation` 默认 `""` = *跟随全局*。全局一旦设成 `isolated`
  （PCL2 / HMCL 转来的用户几乎都会开），**外来实例**（原地接管 / 复制导入的
  `.minecraft`，`version_id` 非空、版本 json 在 `versions/<id>/` 下）也会被
  重定向到 `<mc>/versions/<id>`；但它的存档、模组、`options.txt` 全在 `<mc>/` 根上。
- **两个可复现表现**：
  1. **存档消失**：玩家用 PCL2 玩了半年的 `.minecraft` → AC 导入 → 开全局隔离 →
     进游戏「没有世界」。文件都还在 `<mc>/saves`。
  2. **整合包写错目录**：`src/modpack_import.py:184` `install_mrpack(path, inst.mc_dir)`、
     `:417/:434` `_copy_tree(mc_dir, inst.mc_dir)`、`src/pages_instances.py:3320`
     —— 写入点用 `mc_dir`，游戏读取点用 `game_dir`。实测：
     ```
     mods 实际写入点: …\.minecraft\mods
     游戏实际读取点: …\.minecraft\versions\1.20.1\mods
     一致吗 -> False
     ```
- **最小修法**（两处都要，缺一不可）：
  1. **导入外来实例时显式写 `isolation="default"`**（`import_external` 的 copy / link
     两条分支 + `modpack_import` 新建实例），让全局设置不再影响「别人的布局」；
  2. 整合包 / mrpack 的**写入点全部改用 `inst.game_dir`**，与 UI 读取口径一致。
- **对照**：Prism 只有 `gameRoot()` 一个口径，且导入的实例显式记自己的
  `overrideGameDir`，不会被全局设置改写。

### P1-5 · 离线账号 UUID 是**随机 hex**，不是标准离线 UUID · 已确认

- `src/login_dialog.py:618-623` 建离线账号传 `"uuid": ""`
- `src/accounts.py:33-50` `launch_identity()` 取 `acct.get("id") or acct.get("uuid")`
- `src/accounts.py:145-152` `add()` 里 `acct.setdefault("id", _new_id())`，
  而 `src/accounts.py:29-30` `_new_id()` = `uuid.uuid4().hex[:12]`
- **结果**：传给游戏的 `--uuid` 是 12 位随机 hex，不是 `OfflinePlayer:<name>` 的 v3 UUID。
- **后果**：① 同一个人在 AC 与 HMCL/PCL 里进同一离线服被当成**两个人**
  （背包 / 领地 / 权限全对不上）；② 删账号重建或换机器 → `id` 重新生成 → 身份再变；
  ③ Paper 等服务端对非 UUID 格式的 `--uuid` 会告警或踢。
- **根因**：账号记录的 `id`（AC 内部主键）被当成了游戏 UUID。
- **最小修法**：`launch_identity` 里对 `type == "offline"` 且无 `uuid` 时算
  `uuid.UUID(bytes=md5(("OfflinePlayer:"+name).encode()).digest(), version=3)`。

### P1-9 · 只缺 natives 分类器 jar 时既**不补库也不解压** → `UnsatisfiedLinkError` · 已复现

- `src/launch.py:572-586` `_needs_repair()`
  ```python
  purely_natives = [p for p in missing if re.search(r"-natives-....jar$", basename(p))]
  return len(purely_natives) < len(missing)      # 全是 natives → False → 不修
  ```
  注释的假设是「natives jar 只是 dll 容器，dll 已解压，JVM 不从 classpath 读它，
  缺了可安全忽略」。**但 `_prepare_natives`（`:623-655`）正是从这些 jar 里解压 dll**：
  jar 不在 → `extract_natives` 抛错 → `on_repair()` 被调，而补库被 `_needs_repair` 挡掉
  → 第二次仍失败 → 返回 `None` → 不设 `nativesDirectory` → `java.library.path` 指向空目录。
- **实测**（`_scratch/_probe_natives_deps.py`）：
  ```
  只缺 natives dll 容器      _needs_repair = False -> **不补库（直接放过）**
  只缺普通库                 _needs_repair = True  -> 会去补库
  natives + 普通库混合       _needs_repair = True  -> 会去补库
  ```
- **玩家感受**：启动秒退，崩溃分析报 `UnsatisfiedLinkError: no lwjgl in java.library.path`。
- **最小修法**：`_needs_repair` 对 natives 也应返回 True（先把 jar 补下来），
  或者在 `_prepare_natives` 失败时把缺失的 natives jar 单独走一次补库。
- **对照**：Prism `launcher/minecraft/launch/` 启动前会 `ensureNatives()` 且缺 jar 直接判实例损坏。

### P1-11 · 安装加载器用裸 `java` 兜底，与启动链口径相反 · 已确认

### P1-12 · `optional` 依赖被当成必需前置 → 全量误报「缺少前置」· 已复现

### P1-13 · 安装「假成功」：库/资源下载失败被吞，界面照样跳到 100% 完成 · 已确认

- **链路已查清**（不要把锅算在 mll 那句 `except: pass` 上，分工如下）：

  | 位置 | 行为 |
  |---|---|
  | `venv/.../minecraft_launcher_lib/_helper.py:73-74` | `if r.status_code != 200: return False` —— **返回 False，不抛** |
  | `venv/.../install.py:76-79` | `try: download_file(...) except Exception: pass` —— 只包住**版本 jar**，且吞的是异常 |
  | `venv/.../install.py:86-90` | libraries / natives 分类器 / `extract_natives_file` —— **完全不在 try 里**，但拿到 `False` 也不当回事 |

- **AC 侧还有一层加剧**：`src/core/install.py:73-74` 的 `except Exception: pass` 包住
  `install_launcher`，`src/launch.py:1238-1241` 的 `except Exception` 又把补库失败

### P1-14 · 整合包从资源中心下载时被丢进 `mods/`（不是实例根）· 已确认

- `src/pages_browse.py:392-397` `_TYPE_SUBDIR` 只有 4 个键（mod / shader /
  resourcepack / datapack），**没有 `modpack`**；两处消费点都用
  `_TYPE_SUBDIR.get(self._category, "mods")` 兜底：
  `src/pages_browse.py:1218`（列表页下载）、`:1198`（详情页面板的 `subdir` 参数）
- 于是从资源中心点一个整合包 → 落盘 `<inst.game_dir>/mods/<slug>-<ver>.mrpack`
  （或 CF 的 `.zip`），随后才弹整合包导入框。
- **精确边界**（复核后收窄，勿夸大）：`download_mod_version_to` 按
  `item["filename"]` **原名落盘**，整合包项目通常只有 1 个主文件；只有玩家在
  「前置要不要一起装」里选「是」才会追加依赖 jar，而整合包 `required` 一般为空。
  所以是**一个归档文件**，不是「一批版本不符的 jar」。
- **后果**：Forge/NeoForge 只扫 `*.jar`，这个 `.mrpack/.zip` 会被忽略 —— **不会直接崩游戏**，
  真正的伤害是：界面提示「已下载 xxx.mrpack」，玩家以为装好了，
  **游戏里却没有任何整合包内容**，而且这个文件永远不会被清理。
- **最小修法**：`_TYPE_SUBDIR` 加 `"modpack": ""` 并让 `os.path.join(game_dir, "")`
  落到实例根（或干脆给 modpack 走 `data/downloads/` 临时目录，导入成功后删）。

### P1-15 · 列表页连点下载：两个 worker 写同一路径 + 元数据串台 · 已确认

## 5. 四域对照总表（AC vs HMCL vs Prism vs PCL2-CE）

### 5.1 AC 明确更强，不要回退

| 能力 | AC | 第三方 |
|---|---|---|
| 下载完整性 | 单遍 sha1 + `.part`/Range 续传 + 来源健康表 + 429 `Retry-After` | Prism `NetJob.cpp:67-81` 整组固定重试 3 次、404 不重试；PCL `FileDownloader.cs:89-92` 关自动续传 |
| Java 探测 | 整盘扫描 + 双槽缓存（`core/java.py:102-176`） | Prism `JavaUtils.cpp:452-495` 白名单目录 |
| 崩溃归因闭环 | 扫 mod 清单并自动补缺失依赖（`crash_analysis.py:380-507`） | HMCL/PCL 只有规则表 |
| 实例接管 | 原地接管 PCL2/HMCL/Prism 目录且绝不改真实文件 | Prism 只认自己的实例；HMCL 需手动指目录 |
| 资源中心免 key 通道 | keyless / cfwidget 三通道兜底 | 都需 API Key 或官方账号 |
| 更新安装 | sha256 + size + 原子替换 + 可取消（`core/update_install.py:60-150`） | 普遍只校 size |

### 5.2 AC 明显更差 / 口径不同

| 维度 | AC 现状 | 第三方做法 | 条目 |
|---|---|---|---|
| 删除运行中实例 | 不拦，边跑边删 | Prism/HMCL 先判 `isRunning()` | **P0-1** |
| 路径口径 | `mc_dir` / `game_dir` 两套并存（83 处 mc_dir、13 处 game_dir），且两处各写一份解析逻辑 | Prism 只有 `gameRoot()` 一个口径 | **P1-4 / P2-11** |
| 实例备份范围 | 整个 `mc_dir`（含 assets 联接池） | 只收用户内容 | **P1-3** |
| 备份进度/取消 | 无 | Prism `AbstractTask` 全带进度与取消 | **P1-8** |
| 按钮状态机 | 调用方手工 enable/disable，7 个早退分支漏恢复 | Prism `LaunchController` 集中状态机 | **P1-2** |
| 离线 UUID | 随机 12 位 hex | HMCL/PCL 都算 `OfflinePlayer:<name>` v3 UUID | **P1-5** |
| natives 缺失判定 | 全缺 natives 时判「可忽略」→ 不解压 | Prism 缺 jar 判实例损坏 | **P1-9** |
| Java 错误归因 | 路径失效报成「缺兼容 Java」 | HMCL 分开报 | **P1-10** |
| 装加载器的 Java | 裸 `java` 兜底 | HMCL/Prism 强制用匹配版本 | **P1-11** |
| 依赖类型 | `optional` 当必需 | HMCL 区分 required/optional | **P1-12** |
| 崩溃规则 | 7 条粗粒度（`crash_analysis.py:46-112`） | PCL 29+ 具名成因 + 置信度；HMCL 约 70 条 | round-225 P2-14，未修 |
| Java 兼容约束 | 单一区间 | HMCL `JavaVersionConstraint.java:35-276` 14 条 + ARM64 + Forge 补丁 | round-225 P1，未修 |
| 版本 json 继承 | 交给 mll（只合一次） | HMCL 递归 resolve + 环检测 + patches 按 priority 合并 | round-225 P1-10，未修 |
